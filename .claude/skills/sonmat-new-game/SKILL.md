# sonmat-new-game

새 게임 하나를 "사용자가 켜서 느껴 볼 수 있는 1차본"까지 **한 번에** 가져간다. 중간에 넘기지 않는다.

**1차본 = 아래가 다 된 것**: 훅이 켜진 그 게임 안에서 실제 이벤트로 검증됨 → 게임 자체 음원으로 만든 진동 → 패드 스피커 → 트리거 → 컷씬 트랙 → 장소 효과 → PC 반영·엔진 인식. 그린 파형만 깔아 놓은 것은 1차본이 아니다. 안 된 칸이 있으면 왜 안 됐는지와 무엇이 있어야 되는지를 적어 넘긴다.

일은 둘이다.
- **A. 받아 오기(게임마다 다름)** — 훅을 어떻게 걸지, 어떤 소리가 무엇인지 알아낸다. 매번 조사다.
- **B. 만들기(매번 같음)** — A 가 넘긴 데이터로 햅틱·트리거·패드 스피커를 만든다. 사용자에게 느낌을 묻지 않고 끝까지 만든 뒤 넘긴다.

A 와 B 사이에 **받아 온 것 표**(`profiles/<id>/intake.md`)가 있다. B 는 이 표만 보고 일한다.

**어디에 무엇이 있나** (`sonmat-prj/` 기준)
- 규칙·상태·다음 할 일: `sonmat/WORKLOG.md`
- 엔진 `sonmat/hapticsd.py`, 음원 준비 `sonmat/tools/soundprep/`, 엔진 비교 `sonmat/tools/enginetest.py`
- 초기 모델 `sonmat/data/model.json`, 트리거 프리셋 `sonmat/data/trigger_presets.json`, 거친 정도 표 `sonmat/data/haptic_templates.json`
- 프로필: 게임 레포 `sonmat-game-<id>/`, 만드는 중이면 `sonmat-maker/profiles/<id>/`. `haptics.json`(느낌)·`hook.json`(연결)·`game.json`·`intake.md`
- 엔진별 훅·음원 노하우: 같은 폴더의 `engines.md`. 보정 사례: `calibrations.md`

## 시작 전에 거르기
1. **대상인가**: 안티치트·온라인으로 막힌 게임만 뺀다. 듀얼센스를 이미 지원하는 게임도 보강 대상이다(PCGamingWiki 는 그 게임이 이미 무엇을 내는지 보는 용도). 사용자가 가진 게임인가.
2. **안티치트**가 있으면 접는다고 먼저 말한다. 오프라인 전용으로 돌리는 길이 있어도 사용자 결정 사항이다.
3. **소리 이름이 읽히는가**: 번호뿐이면 일이 몇 배다. 이름표를 먼저 찾는다(A-3).

## A. 받아 오기

### A-1. 읽기만으로 하는 day-0 조사 (게임을 켜지 않고)
PC 설치 폴더를 읽기만 해서 채운다. 추측하지 말고 파일에서 확인한다. 모르면 검색 먼저.

| 볼 것 | 어떻게 | 왜 |
|---|---|---|
| 소리 엔진 | 실행 파일·폴더의 문자열(`AK::`, `Wwise`, UE `SoundCue`, MAME 롬) | 어댑터를 고른다 |
| 소리 이름 | 게임 파일의 큐 이름, 공개 이름표(`bnnm/wwiser-utils` 의 `wwnames/<게임>.txt`), MAME 은 번호 | 규칙을 이름으로 쓸 수 있는지 |
| 음원 보관 | pak(키 필요?) / 낱개 `.bnk`·`.wsp` / cpk·dat / 롬 | 리더를 고르거나 새로 쓴다 |
| 입력 방식 | 실행 파일에 `XInputSetState` 만 있으면 XInput 전용 | Steam Input 을 켜야 하고, 그 진동이 우리 햅틱을 막을 수 있다 |
| 실행 파일 보호 | 코드 구역 엔트로피(8.0 근처 = 스팀 포장으로 암호화) | 함수는 켜진 게임의 메모리에서만 찾는다 |
| 게임 자체 진동 | 패드에 직접 쓰는지, 컷씬 진동 표가 있는지 | `keep_haptics`, 게임 옵션 끄기 안내 |
| 원래 진동 정의 | 게임 파일에 남은 진동 표, 콘솔판 것까지(유니티 `NXRumbles`+`.bnvib`, 언리얼 `ForceFeedbackEffect`, 프롬 `rumblebnd`, 유니티 설정의 `*VibrationFrame`, Wwise `Motion_*`·`HAP_*`). 문자열 훑기로 먼저 찾는다 | **어느 순간이 진동하는가 = 분류 근거.** 그 소리들을 모델 칸에 넣는다. 파형·세기는 가져오지 않는다 |

### A-2. 훅
엔진별로 이미 있는 훅·이벤트 줄 형식·함수 찾는 법은 `engines.md` 의 훅 표를 본다. 새 엔진이면 새 레포 `sonmat-hook-<이름>`(CI 빌드, 태그 `v*` = 릴리스 zip) → `sonmat-games/parts.json` 에 한 줄(주소·sha256·files) → `hook.json` 의 `native.dll`. 앱 메인에 DLL 소스를 넣지 않는다.

- **인자 형식을 확인하기 전에는 걸지 않는다.** 게임을 한 번 죽이면 신뢰를 잃는다.
- 처음 붙일 때는 **타이틀 화면에서**, 저장 안 된 진행이 없는지 확인하고. 세이브가 없는 구간으로 시작하는 게임은 "튕기면 처음부터"라고 미리 알린다.
- 시험 프로세스 통과는 "튕기지 않는다"까지만 말해 준다. 게임이 같은 방식으로 부르는지는 켜 봐야 안다(세키로: 시험에선 이름이 나왔는데 게임은 묶음을 이름 없이 올려 전부 `(null)` → 첫 판 무진동).
- 첫 실행 뒤 가장 먼저 볼 것은 훅 상태 파일이 아니라 **이벤트 파일의 내용**: 줄이 오는가, 이름이 읽히는가, 규칙에 걸리는가. 소리가 실제로 지나가야 검증된 것이다.
- 게임 안에서 한 번도 안 돌린 훅은 사용자에게 **"손맛 켜고 이 게임을 해 본 적이 없다"**고 말한다("훅을 안 돌렸다"는 분석 단계처럼 들린다).
- **훅은 소리가 지나가는 길에만 건다.** 무엇을 장착했나 같은 게임 상태를 알자고 다른 함수를 걸거나 메모리를 읽자고 제안하지 않는다. 쓸 때 나는 소리로 상태를 기억하는 것(프로필 `state`)까지만. 그것도 번거로우면 구분 없이 하나로 둔다.
- **소리 끝도 받는다.** 컷씬 트랙처럼 "그 소리가 나는 동안"만 유효한 것은 시작만으로는 끝을 모른다. 소리 시작 함수와 함께 소리 종료도 찾는다(엔진별 현황은 `engines.md`).
- 켜진 게임에서 읽어 온 코드 사본은 끝나면 지운다. 포장을 벗기는 도구는 쓰지 않는다.
- 훅 주소·패턴 같은 분석 결과는 게임 레포의 `hook.json` 에 둔다(바이트 패턴 파일도 게임 레포, `native.sigs_file`). 게임 폴더에만 있는 손 파일을 만들지 않는다.

### A-3. 소리가 무엇인지
- 이름이 읽히면 이름으로 분류한다. 번호뿐이면 `engines.md` 의 해당 엔진 절.
- **누가 낸 소리인가**: 소유자 이름(언리얼) → 게임 오브젝트 번호(내 발소리를 내는 오브젝트가 나) → 이름 접두(`pl`/`em`) → MAME 은 버튼을 누른 패드. 적·물건 쪽까지 풀어서 가리지 않는다.
- **이름에 주인이 없으면 그게 품질을 정한다.** `pl0000_…` 처럼 주인이 있으면 내 것만 울리지만, 재질 이름뿐(`foot-soil`, `swing-katana`)이면 적의 발소리·칼질까지 내 것으로 울린다. intake 의 "나/남 구분법"이 "없음"이면 넘길 때 그렇게 말하고, 거리(소리 위치와 듣는 위치) 같은 대체 수단을 같이 넣는다.
- **이름에서 뜻을 지어내지 않는다.** 사용자는 그 말을 사실로 듣고 그 위에 요구를 얹는다. 이름으로 짐작한 것은 "이름으로 본 짐작"이라고 붙이고, 앞뒤에 오는 소리(순서)로 확인한 것만 사실로 말한다.
- **여러 이벤트가 음원을 같이 쓴다.** 스피커용 음원을 뽑은 뒤 "이 음원을 쓰는 이벤트가 또 있는가"를 센다(안 그러면 같은 음원을 쓰는 휘두름이 매번 스피커로 나간다).
- **이벤트 이름이 번호뿐이어도 음원 파일의 이름을 본다.** 묶음 안 소리에 원본 파일 이름이 남아 있으면, 훅을 이벤트가 아니라 실제로 재생되는 소리 단위에 건다.
- **끝까지 번호뿐인 소리는 모양으로 가른다**(`soundprep` 의 `looks_like_impact`): 2초 이하, 0.04초 안에 오르고, 30~500Hz 에 힘이 있는 것만 타격으로 보고 낮은 세기(0.6)로. 나머지는 뺀다. 발소리처럼 번호 범위로 알 수 있는 것은 규칙으로 먼저 잡는다(안 그러면 타격으로 들어간다).
- **"가장 큰 순간"의 이름은 첫 판 기록으로 확정한다.** 크게 넣어 둔 이름이 한 번도 안 오고, 진짜는 평범한 칸에 있을 수 있다(니어 저스트 회피 = `core_pl_avoidance`, 적 공격 → 회피 → 이 소리 → 반격 순서). 첫 판 뒤 `style.top`·스피커 규칙이 실제로 몇 번 걸렸는지 세고, 0번이면 그 순간 앞뒤 순서에서 후보를 찾는다.
- **이름표에 없는 번호가 많이 오면 핵심 소리일 수 있다**(니어는 좌우 발소리가 이름표에 없는 번호 둘이었다). 훅이 붙으면 이름 없는 번호를 횟수순으로 뽑아 상위 몇 개를 앞뒤 소리로 가린다. 횟수가 비슷한 둘이 번갈아 오면 좌우 발이다.
- **바닥이 발소리와 따로 오는 엔진**(Wwise 스위치)은 스위치 훅이 있어야 바닥별 발소리가 된다. 못 찾았으면 넘길 때 "철창·물·숲을 걸어도 차이가 없다"고 말한다.
- 소리가 없는 동작(잡기, 착지)은 MAME 이면 RAM 으로, 다른 엔진에서는 1차본에서 뺀다.
- **빈도는 기록이 있어야 안다.** 기록이 없으면 intake 에 "빈도 미확인"으로 적고 B 에서 보수적으로 잡는다. 기록을 얻자고 사용자에게 플레이를 시키지 않는다 — 훅을 붙여 두면 다음 판에 쌓인다.

### A-4. 음원 꺼내기 — 훅과 같은 날 한다
절차는 하나다: 찾기 → 컨테이너 열기 → 목록 → 디코딩 → 48kHz 모노. 게임별로 다른 것(파일명·경로)은 프로필 `source` 에 적는다. 리더별 노하우는 `engines.md`.

- 프로필 안의 데이터 파일(트리·레이어·이름표·규칙)은 **그 폴더 기준** 이름(`"trees.json"`), 소리 폴더는 **`sounds/<id>/` 기준** 이름(`"hap"`, `"spk"`, `"seq"`)으로 적는다(`sonmat_paths.py`). 소리·추출본은 `sounds/<id>/` 에만 쌓이고 git 이 보지 않는다.
- 리더가 없으면 `sonmat/tools/soundprep/` 에 모듈 하나를 추가하고 `READERS` 에 한 줄 넣는다.
- 아카이브는 우리 코드로 풀지 않는다. 공개 언패커를 라이선스부터 확인하고 사용자 PC 로 받아 쓴다(`sonmat/data/fetch_tools.json`).
- 추출본·키는 배포하지 않는다.
- 칸마다 "이름 수 / 게임에 있는 수 / 음원이 풀린 수"를 세어 빈 곳을 본다. 이름으로 넣은 소리 하나가 안 만들어지면 끝까지 따라간다. 효과음 본체를 찾을 때까지 "음원을 꺼냈다"고 하지 않는다.

### A 의 산출물: `intake.md`
한 장. 항목마다 **확인됨 / 추정 / 미확인**.
1. 훅: 엔진, 붙인 방법, 이벤트 줄 형식, 검증 여부
2. 이름표: 출처, 개수, 분류별 개수(타격·맞음·회피·착지·발소리·적·UI·음악·대사·컷씬)
3. 나/남 구분법
4. 바닥·상태 신호(스위치, RAM)
5. 음원: 어디서 어떻게, 개수, 암호화
6. 게임 자체 진동·입력 방식·실행 조건(Steam Input, 옵션)
7. 빈도 기록 유무
8. 못 한 것

## B. 만들기 — 기준 → 초기 모델 → 그 게임의 프로필

1. **기준**: 전투·이동·사격·컷씬이 각각 어떻게 느껴져야 하는가. 스텔라 블레이드에서 잰 값과 사용자가 고쳐 준 것이 근거다.
2. **초기 모델**(`sonmat/data/model.json`): 기준을 숫자와 파형으로 옮긴 것 — 기준 문장(`standards`), 기본값(`defaults`), 공용 파형(`waves`), 파형의 거친 정도 짝(`wave_kinds`), **칸**(`slots`: 패링·타격·회피·발소리 … 각 칸의 파형·세기·성격).
3. **그 게임의 프로필**: 게임이 말해 주는 건 "내 소리 중 어느 것이 어느 칸인가"뿐이다. `game.json` 에 머리말(실행 파일·엔진, 훅은 `"hook"`)과 `slots: {칸: 이름 정규식}` 을 쓰고 `python3 sonmat-maker/tools/new_profile.py <id>` 를 돌리면 `haptics.json`(느낌)과 `hook.json`(연결: 훅 DLL·바이트 패턴·UE4SS 설정과 이 빌드의 VTable·시그니처. 설치 도구는 이것만 보고 게임 폴더에 통째로 쓴다)이 나온다. 그 뒤로는 손으로 고친다.

기준이 바뀌면(사용자가 "이건 전 게임에 이렇게") 모델을 고친다. 한 게임만의 사정이면 그 프로필만 고친다. `haptics.json` 에는 데이터만 둔다 — 경위 메모는 `WORKLOG.md`·`intake.md` 로.

### 칸에 넣기 전에: 조작과 장르 구조
이름만 보고 칸을 채우면 게임의 뼈대를 놓친다(탄막과 액션이 같이 있는 게임에 액션 칸만 채우는 식). `game.json` 의 `_controls_note` 에 먼저 적는다.
- **버튼 배치**: 약공·강공·점프·회피·사격·록온이 어느 버튼인가. L2/R2 에 걸린 동작. 누르고 있는 버튼(연사).
- **장소**: 스테이지마다 탈것·물·눈·늪 같은 구간(기준 2-1).
- **모드**: 3D 액션 말고 무엇이 있나(횡스크롤·탑다운, 비행 슈팅, 해킹, 탈것). 모드마다 이름 접두가 다른 경우가 많다.
- **스킬·무기 체계**: 무기 종류, 차지·저스트 회피·처형 같은 고유 동작. 그 게임의 "가장 큰 순간"이 무엇인가.
- 아는 게임이어도 **이 설치본에서 읽은 것과 일반 지식을 구분해** 적는다. 모르면 검색한다.

### 기준 1. 전투
- **최대 세기는 아끼지 않고, 머무는 시간을 아낀다.** 강타는 0.05초에 올라 0.06초 만에 1/3, 0.4초 만에 1/10(스텔라 블레이드는 최대치를 분당 18번). 엔진의 `style: sb` 가 센 타격만 52Hz 몸통을 깔아 이렇게 다시 그린다.
- 천장에 닿는 건 그 게임의 **가장 큰 순간 서너 종류뿐**: 패링/저스트 회피, 마무리 일격, 적 그로기(`style.top`).
- **어디서 울릴지는 이름(규칙), 어떻게 울릴지는 그 소리.** 음원이 있으면 그 소리를 30~500Hz 로 거른 진동이 나가고, 그린 파형은 음원이 없을 때의 대비다. 진동 대역이 빈 소리(벨·불꽃)는 세기 곡선을 160Hz 에 싣는다.
- **같은 소리는 같은 세기.** 게임에 없는 세기 차이를 지어내지 않는다. 무게는 이름이 다를 때만(S/M/L, 무기).
- **원음이 기본, 소리 없는 것은 우리 진동, 거친 정도만 기준 게임에서.** 소리가 있는 이벤트는 그 원음이 진동이다. 소리가 없는 것은 우리가 상황에 맞춰 만든 진동(빠르기·길이·박자·세기, 재질·거리·크기 구분)이다. 둘 다 손대지 않는다. 기준 게임에서 가져오는 것은 **그 음높이에서 얼마나 거친가** 하나다: `haptic_templates.json`(76종)에서 상황에 맞는 종류를 골라 프로필 `rough` 에 적는다(파형 이름 → 종류). 타격 몸통은 `style.rough`, 럼블 재현·비·천둥이 있으면 `ffb.kinds`·`weather.grains`·`weather.rumble` 의 `rough`. 공용 파형은 `new_profile.py` 가 `wave_kinds` 로 써 준다. **그 게임만의 파형은 하나씩 그 상황을 보고 고른다** — 평균 모양으로 갈아 끼우지 않는다. 고르기 어려우면 적지 않는다(깨끗한 사인 그대로).
- 내가 맞는 것은 내가 치는 것만큼 분명해야 한다(맞음 0.5~0.6, 크게 맞음·쓰러짐 0.9).
- **패드 스피커**: 그 게임에서 **가장 드물고 큰 순간 한두 종류**에만(세키로 = 인살의 쿵 하나, 니어 = 저스트 회피·방패 깨짐·포드 통신). 자주 나는 것(칼 맞부딪힘, 휘두름, 불꽃)은 올리지 않는다 — 진동으로 충분하다. 300Hz 아래를 자르고, 넘치면 전체를 줄인다. 세기는 **0.7 에서 시작**. **`speaker` 는 항상 `"all": false` + `"allow": <정규식>`** — `all: true` 는 음원을 같이 쓰는 엉뚱한 이벤트까지 보낸다. 둘 다 없으면 엔진이 전부 버린다.
- **전체 세기(`master`)는 1.0 에서 시작.** 앱 슬라이더가 100 이 끝이라 그 위는 타격 자체의 세기로 올린다.
- **게임 파일에서 꺼낸 값을 프로필에 두지 않는다.** 게임이 실시간으로 알려 주는 것(효과 이름·길이)만 받고, 모양·세기는 프로필의 우리 값(`ffb.kinds` 등)으로 그린다. "나중에 우리 값으로 바꿈"으로 미루지 않고 넣는 날 끝낸다.
- **트리거**: 그 동작이 실제로 L2/R2 에 있을 때만. 유지되는 동작은 저항(`resist`), 한순간은 한 번 차는 떨림(`vibrate` 9Hz·0.13초). `hold`/`until` 없이 넣지 않는다. 총·손 무기·도구는 `trigger_presets.json`. **트리거에 도구가 걸려 있으면 1차본에 넣는다.** 쏘는 순간을 모르면 게임 내내 걸어 둔다(`"match": "."`, 프리셋 `tool`). 누르고 있는 동작(채널링)이 소리로 잡히면: 켜진 동안 묵직, 모을수록 뻑뻑, 쏘면 풀림.

### 기준 2. 이동
- 움직임은 알리는 게 아니라 **느껴지는 정도**다. 휘두름·회피·점프·착지는 그린 파형으로 낮게(0.15~0.35), 타격처럼 다시 그리지 않는다(`style.skip`).
- **평지는 조용히**: 그린 발소리, 전투 중에만. **느껴지는 바닥(눈·모래·풀·물·얼음)만** 그 발소리로 만든 진동을 전투 밖에서도(0.26~0.36). 바닥이 스위치로 오는 게임은 그 스위치를 잡아야 한다.
- 게임 내내 1초에 한 번 넘게 오는 것은 빼거나 0.2 아래로 둔다(다른 진동을 덮는다).
- 타격은 세게, 이동은 낮게 시작한다. 다 올리면 방해되는 게임이 있다.

### 기준 2-1. 장소 (탈것·물속·눈밭·늪처럼 "지금 어디에 있나")
- **말하지 않아도 1차본에 넣는다.** 사용자가 해 보고 "차 효과가 없다"고 하면 늦은 것이다.
- **스테이지 목록부터 읽는다**: 구간마다 탈것, 물(얕은 물·수중), 눈·모래·늪, 무너지는 바닥, 달리는 열차가 있는지 조사해 `game.json` 의 `_places_note` 에 적는다. 제목에 들어간 것(캐딜락 = 차)은 반드시 있다.
- **상태를 잡는다**: 장소는 이어지는 상태다. 소리 이름·스위치로 오면 그것으로, 안 오면 메모리 값으로(MAME 은 `engines.md`).
- **만드는 것 세 가지**: ① 그 상태인 동안 깔리는 진동(프로필 `beds`: on/off 이벤트 사이에 파형 반복) ② 그 안에서의 걸음 ③ 들어가고 나올 때·부딪힐 때의 사건.
- 세기: 깔리는 것은 타격 밑에 숨는다(엔진 0.2~0.3, 물결 0.1 안팎, 걸음 0.3). 사용자 끄기 항목은 `weather` 와 같이 간다.

### 기준 3. 사격 (탄막·비행·해킹처럼 쏘는 구간)
- 액션 기준만 쓰면 이 구간은 무음이거나 윙윙거린다. 따로 본다.
- **내가 누르고 있는 연사는 질감이다.** 발마다 옅은 틱, 초당 8번쯤으로 솎고(규칙 `gap` 0.12), 최대 0.1 안팎. 타격·회피를 덮으면 안 된다.
- 한 발짜리 큰 사격(레이저·미사일·차지 샷)은 사건 하나: 틱이나 짧은 쿵.
- 내 탄이 맞는 소리는 **적의 탄과 이름으로 구분될 때만**, 아주 작게 솎아서. 모르면 뺀다.
- 탄막에서 가장 중요한 건 **맞는 것과 곧 맞을 것**: 내 피격은 근접전만큼 세게, 큰 공격의 예고는 낮게 부풀고, 발사는 쿵.
- 처치는 폭발이 전한다: 이름의 소·중·대대로.

### 기준 3-1. 세계 (내 동작이 아닌데 몸으로 오는 것)
- 원래 게임이 진동하는 순간 중 전투·이동 칸에 안 맞는 것: `quake`(땅·바다가 움직임: 지진, 파도, 거인의 발 구르기), `roar`(큰 괴성·포효), `warp`(순간이동), `hold`(켜져 있는 동안 계속 나는 소리: 불, 분사).
- `hold` 는 소리가 이어지는 동안 우리 파형이 이어지고, 게임의 멈춤(`Stop_<이름>`)에 끝난다. 멈춤이 안 오면 `max` 초에 끝.
- 원래 진동 표(A-1)가 있으면 그 표의 순간을 빠짐없이 칸에 넣는다.

### 기준 4. 컷씬
- 컷씬이 비면 반쪽짜리로 느껴진다. 모든 장면에 트랙을 만든다.
- **충격 위주**: 장면 자체의 평균보다 튀는 것만 통과시키고(게이트), 깔리는 떨림은 조금만(`keep` 0.15). 음악 전용·대사 전용 묶음은 뺀다.
- 장면 최댓값이 0.65 안팎이 되게(`pct` 90, `gain` 2.0). 4kHz 로 저장하고 처음 쓸 때 읽는다.
- **컷씬의 끝 = 그 컷씬 소리가 끝나거나 꺼질 때**(모든 엔진 공통). 끝까지 봤든, 건너뛰었든, 못 건너뛰는 컷씬이든 이것 하나로 맞는다. 종료 훅이 없는 엔진은 게임이 주는 끝 신호(`cutscene.end`: 장면 끝 이벤트, 음악이 바뀌는 순간)와 내 휘두름·회피로 끝낸다.
- **내 발소리로 끝내지 않는다.** 컷씬 안에서도 캐릭터는 걷는다. "N초 조용했다가 걸으면" 같은 간접 조건을 만들지 않는다.

### 만들고, 확인하고, 넘긴다
1. `game.json` 을 쓴다. 칸 설명은 모델의 `look_for`. 모델에 칸이 없는 것은 `extra_rules`·`waves`·`triggers` 로. 정지 이벤트처럼 이름만 같은 것은 `extra_rules` 맨 앞에서 걸러 낸다.
2. `new_profile.py <id>` → 칸마다 몇 개의 이름이 걸리는지 센다(한 칸에 수백 개면 정규식이 넓다).
3. `python sonmat/tools/soundprep <id> --maker` 로 진동 클립·스피커 소리·컷씬 트랙을 만든다(`sounds/<id>/`). `--maker` 를 붙여야 게임 파일에서 읽은 표(`trees*.json`·`rules_auto.json`)가 게임 폴더에 써진다(안 붙이면 플레이어 PC 처럼 소리 옆에 둔다). **리더가 없으면 지금 만든다.** 피격처럼 이름이 음성(신음)인 칸은 `[정규식, {"drawn": true}]` 로 그린 파형을 쓴다.
4. **패드 없이 확인**: 가짜 이벤트를 엔진에 흘려 칸마다 의도한 파형·세기로 나가는지, 남의 소리·음악·UI 가 조용한지 본다. 엔진을 고쳤으면 `enginetest.py`(모든 게임에 같은 이벤트를 고치기 전후 엔진에 넣어 비교, 같으면 0). 클립 이름 전부를 `kinds` 에 대 보고 종류별로 나열해 엉뚱한 이름을 잡지 않는지 눈으로 본다. 음원 길이가 형제들보다 유난히 짧으면 조각을 놓친 것이다 — 만든 클립의 길이를 나란히 놓고 본다.
5. `sonmat-maker/tools/deploy_pc.sh` 로 목록 확인 → `--go`. 음원 클립은 PC 것을 덮지 말고 새 것만.
   - 엔진 다시 띄우기 = `taskkill pythonw` → `schtasks /run /tn SonmatTray`. 명령을 `&` 로 잇지 말고 따로 보낸다.
   - PC 에서 `soundprep --maker` 를 돌렸으면 그 게임의 `trees*.json`·`rules_auto.json`·표를 맥으로 먼저 가져온다. 안 그러면 다음 `--go` 가 맥의 옛것으로 덮는다.
   - zsh 에서 `scp 파일 $PC:이름` 은 `:c`·`:s` 가 변수 수식어로 먹힌다. `"${PC}:이름"` 으로 쓴다.
6. `WORKLOG.md` 에 적는다: 넣은 것, **느껴 보지 않은 첫 값**이라는 것, 미확인.
7. 사용자에게 넘긴다: 무엇이 울리는지, 실행 조건(Steam Input, 게임 옵션), 아직 빈 것. **빈 것은 "못 받는 신호 → 그래서 무엇이 안 느껴지는가"로 미리 경고한다.** 아래 표를 채워 해당하는 줄을 말한다. "바닥 질감은 없습니다" 한 줄로 넘기지 않는다.

   | 확인 | 아니면 사용자가 겪는 것 |
   |---|---|
   | 내 발소리가 규칙의 이름으로 실제로 오는가(횟수) | 걸을 때 진동이 전혀 없다 |
   | 바닥 종류를 받는가(이름 또는 스위치 훅) | 철창·물·눈·숲을 걸어도 차이가 없다 |
   | 누구 소리인지 가릴 수 있는가 | 적·NPC 의 발소리·칼질에도 울린다 |
   | 소리 이름이 게임 안에서도 읽히는가 | 진동이 아예 없다 |
   | 가장 큰 순간(패링·저스트 회피·처형)의 이름이 확인됐는가 | 그 순간이 평범하게 지나간다 |
   | 컷씬의 끝을 받는가 | 건너뛴 뒤에도 컷씬 진동이 남는다 |
   | 장착·선택 상태를 소리로 알 수 있는가 | 무기·도구를 바꿔도 트리거 느낌이 같다 |
   | 훅을 그 게임 안에서 돌려 봤는가 | 첫 판에 안 울리거나 튕길 수 있다 |

   조절은 앱에서 하고 `settings.json` 에 남는다. XInput 전용 게임은 **Steam Input 을 켜고 게임 옵션의 진동을 끈** 조합에서 햅틱이 정상으로 나온다.

### 첫 판 뒤에 (사용자가 느낌을 말해 주면)
기록부터 읽고 답한다.
1. 그 판의 엔진 기록을 종류별로 센다(무엇이 몇 번 나갔나) + 날것 이벤트를 이름으로 바꿔 센다(무엇이 왔는데 안 걸렸나).
2. `style.top`·스피커 규칙이 걸린 횟수. 0번인 것은 이름이 틀린 것이다(A-3).
3. "과하다"는 스피커부터 본다 — 의도하지 않은 이벤트가 스피커로 나가고 있지 않은지.
4. "끊긴다·깨진다"는 `sonmat-fault-hunt`. 먼저 그 순간의 엔진 기록(늦은 블록·한계 초과)만 확인해 말하고, 음원이나 "효과를 많이 넣어서"를 원인으로 추측하지 않는다.
5. 사용자가 플레이 중에 "방금 OO 했어"라고 하면 그 자리에서 기록 끝을 읽는다. 어느 동작인지 모르겠으면 본 것을 순서대로 보여 주고 묻는다. 사용자가 "멈칫하는 순간" 같은 말을 하면 드물게 온 내 소리를 앞뒤 5개씩 놓고 본다. 귀찮아하면 거기서 접는다.
6. 고친 것이 "비슷한 상황이면 이렇게"로 일반화되면 `calibrations.md` 에 더한다.

## 사용자가 다른 게임을 하는 중이면
- 엔진을 다시 띄우지 않는다. 새 프로필은 다음 엔진 시작 때 읽히니 파일만 놓아 둔다.
- PC 의 무거운 일(음원 디코딩)은 낮은 우선순위로 돌린다(`start "" /belownormal /b /wait`).
- 패드·오디오 장치는 건드리지 않는다. 훅 시험은 무음 출력의 별도 프로세스에서만.

## 하지 말 것
- 사용자에게 수집용·확인용 플레이를 숙제로 내지 않는다. "알아서 해"는 느낌을 묻지 말고 끝까지 만들라는 뜻이다. 게임을 대신 조작하라는 뜻도 아니다.
- 사용자가 플레이 중일 때 패드에 시험음·HID 를 쓰지 않는다. PC 는 읽기만.
- 붙여 보지 않은 훅을 "된다"고 하지 않는다. 느껴 보지 않은 값을 "맞췄다"고 하지 않는다.
- 한 게임에서 나온 문제를 그 게임만 고치고 끝내지 않는다. 같은 구조의 다른 게임에도 있는지 먼저 본다.
- **원래 게임의 진동 파형·세기를 가져다 쓰지 않는다.** 콘솔판 진동 파일·럼블 곡선은 "어느 순간이 진동하나"를 알려 주는 분류 근거일 뿐이다. 분류하고, 그 칸의 우리 햅틱을 낸다.
- 범위를 넓히지 않는다. 1차본은 모델의 칸까지다(전투·이동·사격·컷씬·장소, 특별한 순간의 스피커, 트리거 한두 개). 무기별 손맛, 적별 규칙은 사용자가 느껴 본 뒤에.

## 테스트 시나리오
- 정상: "다음 게임 니어 오토마타" → day-0 표 → 훅 붙임·이름 대조 → `intake.md` → 조작·모드·장소 정리 → `game.json` 칸 채우기 → `new_profile.py` → 음원 클립 → 가짜 이벤트 확인 → PC 반영 → 사용자에게 넘김.
- 에러: PC 가 꺼져 있음 → A-1 은 못 하므로 검색으로 엔진·이름표만 확인하고 멈춰서 알린다(깨우지 않는다). 훅이 게임을 죽임 → 사실대로 알리고, 원인을 고친 뒤 타이틀에서 다시. 음원 리더가 없음 → 리더를 만든다(그게 이 일의 절반이다).
